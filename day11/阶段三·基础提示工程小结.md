---

## 0. 这一站解决的核心问题

抽取层建好后,喂"乖"新闻都对。但真实新闻是**脏的**:有的没具体公司、有的一次提一堆公司、有的是传闻、有的信号互相对冲。薄 prompt("从这条新闻抽取公司、事件、影响倾向")在这些硬骨头上会**自作主张**——而且程序不报错,是**语义层的沉默失败**,pydantic 拦不住(填错的也是合法字符串)。

> 一句话心智:**写 prompt ≈ 给一个能力极强、但极其"按字面办事"的外包 junior 写规格说明书(spec)。** 你含糊,它就拿假设填空;你精确 + 给验收样例,输出就稳定可控。

---

## 1. 痛点实测:薄 prompt 在哪自作主张

| 硬骨头新闻 | 薄 prompt 的错误行为 | 根因 |
|-----------|--------------------|------|
| 宏观无公司(央行降准) | 硬塞 `company='央行'` | 必填 `str` 把模型逼到墙角,不能交白卷 |
| 多公司(立讯、歌尔…) | 挤成一个串 `'立讯精密, 歌尔股份'` | 单值 `str` 装不下,下游匹配股票代码直接断链 |
| 传闻(未证实) | 判中性——但**是运气还是规则?** | 没明文规则,模型每次重新拍脑袋,不可复现 |

**归一句根因**:schema 只约束了「长什么样」(类型),没约束「该是什么」(语义)。判断权全漏给了模型。金融产品里这不可接受——同一条今天利好、明天中性,信号就不可信。

---

## 2. 三板斧:把判断权收回来

这一站最妙的认知:**主战场不在那句 user prompt,而在 pydantic 模型本身**。instructor 路线 = **模型即规格(schema as spec)**,改 schema,instructor 自动翻译成提示词喂模型。

### 斧一 / schema 收口结构与硬约束(最先动、成本最低)

```python
class NewsExtraction(BaseModel):
    companies: list[str] = Field(            # 单值→列表:多公司各自成元素,无公司则 []
        description="新闻直接涉及的上市公司名称列表；若无明确上市公司（如纯宏观/政策），"
                    "返回空列表 []，不要编造或填监管机构名")   # 明文授权"交白卷"
    event: str = Field(description="事件简述，一句话")
    sentiment: Literal["利好", "利空", "中性"] = Field(
        description="判定规则：未经证实的传闻/消息一律判'中性'；利好利空需有明确既成事实支撑")
```

改完只跑同一批硬骨头(user prompt 一字未动),行为全变:
- 宏观 → `companies=[]`(诚实),且 `sentiment` 顺带自洽改判中性(**好 schema 的连锁效应**)
- 多公司 → `['立讯精密','歌尔股份']`(可逐个匹配)
- 传闻 → 中性,这次**有底气**(规则白纸黑字,可复现)

要点:
- **字段名也是提示**。`companies: list` 比 `company: list` 更暗示"放多个"。命名即沟通。
- `description` 不只是文档,instructor 会把它喂给模型 → **它就是写给模型的规则**。
- `response_format` 保证「合法」,pydantic 保证「合规」——职责别混。

### 斧二 / system 消息放"贯穿全局的总纲"

之前 `messages` 里一直没用 system。它和 user 的分工:

| 角色 | 放什么 | 特点 |
|------|--------|------|
| `system` | 人设 + 立场 + 一以贯之的总纲(如"风控口径") | 优先级/稳定性更高,贯穿所有输入 |
| `user` | 具体这一条任务 | 一次一变 |

```python
{"role": "system", "content":
    "你是严谨的金融信息抽取助手，服务于风控场景。"
    "涉及负面指控（造假、违规、调查）的新闻，即使当事方否认，也应按利空处理。"}
```

### 斧三 / few-shot:教那些"说不清但一看就懂"的口径

文字规则有天花板。典型硬骨头:**信号对冲**——

```
"某公司被曝财务造假，但管理层在电话会议中坚决否认相关指控。"
```

既有利空(被曝造假)又有对冲(否认)。两种合理业务口径:
- **口径A 保守**:否认了=没坐实 → 中性
- **口径B 风控**:"被曝造假"本身即重大负面 → 利空(宁可错杀)

`description` 文字很难干净区分(写"被曝负面即利空"会误伤正常中性传闻)。**few-shot 一条示例就拿下。**

```python
messages=[
    {"role": "system",    "content": "...风控口径,负面指控即使否认也按利空..."},
    # few-shot:伪造一段"模型之前已漂亮答过"的历史对话
    {"role": "user",      "content": "...新闻：某药企被监管点名涉嫌数据造假，公司随后否认。"},
    {"role": "assistant", "content": '{"companies": [], "event": "被监管点名涉嫌数据造假，公司否认", "sentiment": "利空"}'},
    # 真正要处理的输入
    {"role": "user",      "content": f"...新闻：{news}"},
]
```

**实测效果**:那条造假新闻 `中性 → 利空`,**且其余四条纹丝不动**。
- few-shot 的本质 = **伪造一段历史对话**,假装模型之前已答过一次标准答案,它接着模仿那个口径。
- `assistant` 那条内容是**一个 JSON 字符串**,要和期望输出格式严丝合缝。
- "只有目标那条翻、别的没动" = 示例选得准,**定点爆破、无污染**。若加示例后别的也乱变 → 示例选偏了/口径太宽。
- 一条好示例能**同时示范多个维度**(这条里 `companies=[]` 顺带强化了"无明确公司"规则)。

## 3. 总骨架(记这张图就够)

```
规格说明书分三层下发，优先级/适用范围/成本各不同：

  pydantic schema  →  结构 + 字段级硬约束（list、Literal、必填可选、description规则）
       ↓                 instructor 自动翻成提示词；成本最低、最该先动
  system 消息       →  人设 + 贯穿全局的总纲（立场/口径）
       ↓
  few-shot 示例     →  教"文字讲不清、一看就懂"的边界口径；成本最高、最后动
```

**心法**:能用 schema 约束的别写进 prompt;能用一句规则讲清的别堆例子;只有"文字讲不清的判断口径"才动用 few-shot。从上到下,成本递增、越来越"软",按需逐级动用。

---

## 4. 实战提醒(上量时会遇到)

- **few-shot 质量 > 数量**:每条示例占 token、拖慢速度;示例口径互相打架会让模型更迷糊。生产一般 **1~3 条精选示例**,挑最易出错的边界情况示范。
- **语义沉默失败**:程序"成功 N/0"≠ 数据对。`company='央行'`、多公司挤一个串,都是合法字符串骗过了 pydantic。**逐值核对要核到"语义对不对",不只是"格式合不合法"。**
- **改 schema = 改行为**:业务规则沉淀在 schema/system/few-shot 里,而非散落在到处拼接的 prompt 字符串中。比 LangChain 拼模板更像"写 Java DTO + 校验注解 + 立场说明"。
